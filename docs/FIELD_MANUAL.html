Routing Optimizer Field Manual

A complete walk through Juspay-Payment-Routing-Optimizer: an adaptive payment router, an LLM agent that diagnoses gateway failures, and the loop between them closed. Written to be studied in order, from no prior knowledge, until you can defend every line of it.

CHAPTER 01

What the project is

Three layers, one loop. Learn this shape first — everything else hangs off it.

A payment fails or succeeds depending on which gateway you send it through, and gateway health changes hour to hour. The project builds three things and connects them:

LayerCodeWhat it does
Routersrc/gateways.py, src/routers/, src/simulator.pyA simulated fleet of five gateways; six bandit strategies compete to route transactions well.
Agentsrc/agent/An LLM with six read-only telemetry tools. Given an alert, it returns a structured diagnosis.
Loopsrc/agent/constraints.py, src/closed_loop.pyA confident diagnosis becomes a routing constraint the router obeys on the next transaction.

Around them sits a production shell: a FastAPI service splitting a microsecond hot path from a multi-second cold path, Redis for shared state, Kafka and ClickHouse for the event stream, Prometheus metrics, a ground-truth eval suite wired into CI as a gate, an off-policy evaluation module, and a small Haskell DSL for constraint files.

The 90-second opening

Say this in the room

“Juspay published a note on control-theoretic payment routing — feedback loops plus multi-armed bandits to steer transactions toward reliable gateways. I didn't reproduce the paper; I took the problem statement and built it to find out what actually happens. Three layers: a non-stationary bandit over a simulated gateway fleet, an LLM agent that diagnoses why a gateway broke from telemetry, and the loop between them closed — a confirmed diagnosis becomes a routing constraint. The headline is +323 bps over a static router. The two most interesting findings are negative: the PID controller does not beat a correctly tuned discount factor, and a contextual bandit beats my LLM agent at every traffic volume I tested. Both are reported rather than tuned away, and I can explain the mechanism behind each.”

That last sentence is the one that separates the project from a portfolio piece. Lead with the negative results — an interviewer who hears you volunteer them stops probing for whether you are hiding something and starts probing for whether you understand them.

Why the layering is the design

The router is a statistical object: it knows which gateway converts best, and nothing about why. The agent is a semantic object: it can say “PG-Delta is declining HDFC cards” — a sentence with a subject and an object, which a Beta posterior cannot express. The constraint layer is the translation between them, and it is deliberately the most paranoid code in the repo, because it is the point where a language model's output moves real money.

Mechanism

Everything in this project is downstream of one asymmetry: the router's own decisions determine the data it collects. Route away from a gateway and you stop learning about it — including the fact that it recovered. That is what makes this a bandit problem rather than a forecasting problem, it is why the constraint layer must leak canary traffic, and it is why the agent's tools return null instead of a success rate when a gateway was starved of traffic. One idea, three consequences.

CHAPTER 02

Payments, from zero

You cannot defend the design without the vocabulary. Ten minutes buys you all of it.

Who is in the chain

merchantThe shop. In this repo, checkout/app.py — “Kirana Cart”, a fictional storefront on port 8001.
PSPPayment Service Provider / orchestrator. This is what Juspay is, and what the router in this repo is. It does not hold the money; it decides where to send the attempt.
gatewayAlso “PG” (payment gateway) or acquirer. The five PG-Alpha … PG-Echo arms. It forwards the attempt onward.
issuerThe customer's bank — HDFC, ICICI, SBI, AXIS, KOTAK. It ultimately approves or declines. This is the axis that makes the hard eval cases hard.

A transaction succeeds or fails. Aggregate that over many transactions and you get the success rate (SR) — the single number the business cares about, because a declined payment is usually an abandoned cart, not a retried one.

Basis points

1 bps = 0.01 percentage point. 100 bps = 1 pp. So “+323 bps” means the success rate went from 91.73% to 94.96%. Payments people quote bps because the differences that matter are small and enormous at once: at 350 million transactions a day, 1 bps is 35,000 payments.

Say this in the room

“The reason SR optimisation is worth an entire engineering org is leverage. Nothing about the merchant, the customer, or the product changes — you are converting a routing decision you were already making into revenue. A 300 bps lift is a 3% revenue lift on payment volume with no new customers.”

Why gateways differ

Real gateways have genuinely different reliability at any moment, for boring operational reasons: maintenance windows, capacity limits, a bad deploy, a broken link to one specific issuing bank, regional network problems. Their pricing differs too — the repo tracks cost_bps per gateway (9–22 bps), because routing purely for SR quietly buys conversion with fees. The README is explicit that cost is tracked and reported but not optimised, and names the real objective as roughly max(SR) − λ·cost − μ·latency.

The failure mode the whole project is built around

A gateway can look fine in aggregate while declining every transaction from one issuing bank. Suppose PG-Delta carries 31% HDFC traffic and starts declining HDFC almost entirely. Its overall success rate falls from 94% to roughly 65% — soft, not dead. Every fleet dashboard shows a slightly unhappy gateway. Nothing shows the actual fact, which is that HDFC cardholders cannot pay.

Segmenting by issuer reveals it instantly. That is why segment_failures is the one tool in the agent's kit that genuinely earns its place, and why partial_degradation vs issuer_outage is the discriminating pair in the eval set.

Two India-specific details worth dropping

  • RBI data localisation. Payment data cannot leave India. That is the stated reason Langfuse (self-hostable) was chosen over LangSmith for tracing — LANGFUSE_HOST points at your own deployment in one line. This is a good answer to “why not just use the standard observability SaaS?”
  • Volume. The 350M/day figure and the 100 ms decision budget both come from the Juspay brief, and they are what justify the microsecond hot path and the “no network call in /route” rule.
CHAPTER 03

The environment

A benchmark is only as honest as the world it runs in. This is where the honesty lives.

src/gateways.py defines the world; src/simulator.py runs a router through it. Two ways to build a simulator that flatters your method, both deliberately avoided:

  • Make it stationary. Then every algorithm converges, differences shrink to noise, and your result says nothing about production.
  • Give it one dominant arm. Then “always route to gateway 3” wins and no adaptation is needed.

So the fleet is built so leadership changes hands at least three times across a simulated week — and there is a test asserting that, rather than leaving it to chance.

The five gateways and what each one attacks

PG-Bravo0.94Best until it hard-outages overnight (×0.05)Detection latency; confident posteriors
PG-Charlie0.90Strong diurnal swing, phase −π/2Slow adaptation; long memory

PG-Echo0.96Genuinely the best — after a bad first day (×0.72)Premature convergence

PG-Echo is the sharpest of the three mechanisms. Any router that stops exploring on day-one evidence writes off the best gateway in the fleet and loses hundreds of bps for the rest of the week. That single spec is what makes “does this strategy keep exploring?” a measurable question.

Ground truth, and the wall around it

def true_sr(self, t, issuer=None) -> float:
    phase = 2*pi*t/TICKS_PER_DAY + self.diurnal_phase
    sr = self.base_sr * (1 + self.diurnal_amplitude*sin(phase))
    for event in self.events:
        if event.active(t, issuer):
            sr *= event.sr_multiplier
    return clip(sr, 0.001, 0.999)

This is the only place the true success rate exists. It is used to generate outcomes and to compute regret against an omniscient oracle. It is never visible to a router, and never visible to the agent. The agent reads TelemetryStore, which exposes only outcomes of transactions that were actually routed — invariant 6 in AGENTS.md. If the agent could read true_sr, the eval would be measuring nothing.

Mechanism

DegradationEvent.active(t, issuer) has one subtle line: if the event names an issuer and the caller asks without naming one — the fleet-level view — the event returns False. The issuer-scoped fault is literally invisible in the aggregate ground truth, by construction. That is not a shortcut; it is a faithful model of what a dashboard shows you.

Ticks vs transactions — decoupled on purpose

A tick is one simulated minute; TICKS_PER_DAY = 1440. Gateway health drifts on the clock. A router's learning rate depends on transaction volume. Holding the calendar fixed while varying volume is precisely how the γ result in chapter 5 is found — and it is the reason the simulator maps transaction i onto a tick with ticks = (arange(n) * n_ticks // n) rather than assuming one per minute.

Vectorised, but honestly so

run_once precomputes a (n_gateways, n_ticks, n_issuers) array of ground truth and draws all random numbers up front, then runs a plain Python loop for the decisions. Two details carry weight:

  • Issuers come from a separate RNG stream (seed + 10_000). Adding the issuer dimension therefore does not perturb the outcome draws, so benchmark numbers measured before issuers existed stay comparable.
  • Regret is computed per (tick, issuer) cell: oracle[ticks, issuers] − sr[chosen, ticks, issuers]. The oracle is clairvoyant and issuer-aware, which is the hardest honest baseline.
Trap

run_once calls router.select(t) with no context and builds Outcome(...) with no issuer. So a ContextualThompsonRouter run through run_once silently degrades to a flat bandit — the class even counts this in updates_without_context for exactly that reason. The contextual experiments use run_closed_loop instead, which does pass both. If an interviewer asks “what would you refactor first?”, this is a strong answer: two nearly-identical simulation loops that have drifted in their context semantics.

CHAPTER 04

Bandits, from zero

Four strategies, one interface. Know why each fails before you learn why each works.

The problem statement

You have k arms (gateways). Pulling an arm returns a reward — here, 1 for a successful payment, 0 for a decline. You do not know the arms' true success probabilities. You want to maximise total reward over a long horizon. The tension is permanent: every pull spent learning about an arm is a pull not spent on the arm you currently believe is best. That is explore vs exploit.

The scoring metric is regret: the reward an omniscient policy would have earned minus what you earned. Good algorithms have regret growing like O(log T) in a stationary world — sublinear, meaning your average loss per decision goes to zero.

Trap

Why not just forecast each gateway's SR with a supervised model and take the argmax? Because the router's decisions select its own training data. A model trained on routed traffic is trained on a sample its own predecessor chose, and it will confidently recommend the gateway it already prefers. The exploration term in a bandit is not a nuisance you tolerate — it is what keeps the dataset informative. This is the single best answer to “why a bandit?” and it is in docs/DESIGN.md §1.

The shared interface

class Router(ABC):
    def select(self, tick, context=None, blocked=frozenset()) -> int: ...
    def update(self, outcome: Outcome) -> None: ...
    def action_probabilities(...) -> np.ndarray: ...   # the propensity
    def decide(...) -> tuple[int, np.ndarray]          # choice + propensity, one pass

Everything is a subclass of this. Note what is not in it: no access to time-series history, no access to true SR. A router sees one outcome at a time and folds it into whatever state it keeps.

Strategy 1 — static-weighted (the baseline you must beat)

Fixed weights, never learns. update() is pass — deliberately blind. This is not a strawman: weighted round-robin negotiated in a commercial agreement is how a large share of real payment traffic is routed. It fails in exactly one way — when a gateway degrades, it keeps sending traffic. Its outage response in the benchmark is literally “never”.

Strategy 2 — ε-greedy

explore = self.rng.random() < self.epsilon
if explore: return random arm
else:       return argmax(counts.mean)   # random tie-break

Simplest thing that adapts. Two weaknesses to name: exploration cost is paid at a constant rate forever (ε=0.10 means 10% of traffic is deliberately sub-optimal on day 1000), and the exploration is undirected — it is as likely to probe an arm it already knows is terrible as one it is genuinely uncertain about.

It is also the only strategy with a genuinely closed-form propensity, which is why the eval telemetry is generated with it at ε=0.25 — see chapter 12.

Strategy 3 — UCB1

bonus  = c * sqrt(2 * log(total_pulls) / pulls_per_arm)
scores = counts.mean + bonus
return argmax(scores)

Optimism in the face of uncertainty. The bonus is an upper confidence bound: it is large when an arm has few pulls and shrinks as evidence accumulates. So exploration is directed — attention flows to genuinely uncertain arms, not random ones. This is strictly better-motivated than ε-greedy and its regret bound is the classic O(log T).

Mechanism

UCB1 is deterministic given its state. Its action_probabilities returns a one-hot vector. That has a consequence people discover far too late: you cannot do off-policy evaluation from a deterministic logging policy. Every unchosen action has propensity zero, so importance weights are undefined and no volume of logs can tell you what a different policy would have earned. If you intend to evaluate policies offline later, the policy you deploy today has to be stochastic. There is a test asserting exactly this. Chapter 15 develops it.

Strategy 4 — Thompson sampling (the winner)

Keep a Beta posterior per arm. To choose, draw one sample from each posterior and take the argmax of the samples.

def _sample(self, inflation=1.0):
    alpha = maximum(self.counts.successes / inflation, 1e-3)
    beta  = maximum(self.counts.failures  / inflation, 1e-3)
    return self.rng.beta(alpha, beta)

def select(self, tick, context=None, blocked=frozenset()):
    samples = self._sample()
    if blocked: samples[list(blocked)] = -inf
    return int(argmax(samples))

Why Beta, specifically

The reward is Bernoulli (success/failure). The conjugate prior for a Bernoulli likelihood is the Beta distribution: if your belief about an arm's success probability is Beta(α, β) and you observe a success, your updated belief is exactly Beta(α+1, β). A failure gives Beta(α, β+1). Conjugacy means the Bayesian update is integer addition — no integration, no gradient, O(1) per observation. At 350M transactions a day that is not an elegance argument, it is the whole reason this is deployable.

Beta(1,1) is the uniform distribution — “I know nothing”. The prior in DiscountedCounts defaults to 1.0 for both, so a cold arm starts uniform and gets explored.

Why Thompson beats UCB1 here

Probability matching. Thompson routes to arm a with probability equal to its posterior probability of being the best arm. That gives smoother traffic allocation than UCB1's argmax: allocation degrades gracefully as evidence accumulates, instead of flipping hard between arms. The docstring names the operational reason — downstream gateways have capacity commitments that hate step changes. That is a systems answer to an algorithms question, and interviewers notice it.

The propensity, and one very sharp detail

Thompson has no closed form for P(argmax), so the propensity is estimated by Monte Carlo. Two rules govern it:

  1. The RNG is supplied by the caller, never taken from self.rng. Sampling from the router's own stream to compute a propensity would change the sequence of routing decisions — the act of measuring would alter what is measured, and every benchmark number with it. This is invariant 12, with a test named test_propensity_computation_does_not_disturb_routing.
  2. decide() draws n_samples + 1 rows and excludes row 0 from the propensity estimate. Row 0 is the decision. Counting the winning draw among its own evidence biases the chosen arm's propensity upward by roughly 1/n — and importance weights divide by that number.
Say this in the room

“The propensity bias is my favourite bug in the repo because it would never have surfaced as a crash or a failing assertion. It would have quietly shifted every IPS and doubly-robust estimate, in a direction that flattered whichever actions the router already preferred. The only way to catch that class of defect is to know what the number is for.”

CHAPTER 05

Non-stationarity and γ

How you remember beats which strategy you pick. This chapter contains the project's best result.

The primitive

DiscountedCounts lives in routers/base.py, not inside any one strategy — because the choice of how to remember turned out to dominate the choice of which strategy. Discounted UCB1 beats undiscounted Thompson. Discounted Thompson beats both.

def update(self, gateway, success):
    if self.gamma < 1.0:
        self.successes = self.prior + self.gamma*(self.successes - self.prior)
        self.failures  = self.prior + self.gamma*(self.failures  - self.prior)
    if success: self.successes[gateway] += 1.0
    else:       self.failures[gateway]  += 1.0

With γ = 1.0 this is an ordinary running tally: evidence from 100,000 transactions ago carries exactly as much weight as evidence from the last second. Correct in a stationary world, wrong in a payments network, where a gateway that was healthy an hour ago tells you very little.

With γ < 1.0, every observation decays the accumulated history, so the counts track an exponentially-weighted recent window. Effective memory ≈ 1/(1−γ) observations. γ=0.999 → about 1,000 observations. γ=0.9999 → about 10,000.

Mechanism

Notice that decay is applied to all arms, not just the played one, and it decays toward the prior, not toward zero. That is deliberate and load-bearing: unplayed arms drift back to Beta(1,1), which re-opens them for exploration after a long absence. Decaying only the played arm would let a gateway written off during an outage stay written off forever — which is precisely the PG-Echo failure the environment was built to punish.

Discounting vs sliding window

A sliding window ("only remember the last N observations") is equivalent in effect and was rejected for one reason: it needs O(window) memory per gateway. Geometric decay is O(1) per arm — two floats. At 350M transactions/day across a large gateway fleet, that is the difference between a cache line and a data structure. The academic reference is Garivier & Moulines (2011), discounted and sliding-window UCB for switching bandits.

The interesting result

Discounted Thompson wins. But the γ that makes it win is not a constant.

Say this in the room

“γ forgets per observation. Gateways degrade per unit time. So the correct γ depends on how many observations fall into a unit of time — which is transaction volume. A merchant doing 20k/week and one doing 100k/week want 0.999 and 0.9999 respectively. A fleet-wide constant is therefore wrong for nearly everyone on it, and getting it wrong costs 50 to 170 bps.”

That sentence reframes the whole exercise. The problem is not “tune a hyperparameter”; it is “you have a per-merchant tuning problem whose cost scales with merchant count, and merchant volume drifts, so it is not a one-time tuning either.” The PID controller in the next chapter is a response to that, not an attempt to build a better bandit.

CHAPTER 06

The PID controller

Control theory applied to a Bayesian posterior — and the bias bug that shaped the design.

PID in sixty seconds

A PID controller drives a measured value toward a setpoint. You compute an error = setpoint − measurement, then a control output:

u = Kp·error  +  Ki·∫error  +  Kd·d(error)/dt
  • P — proportional. Responds to the error now. Alone it leaves a steady-state offset.
  • I — integral. Accumulates past error, so persistent small errors eventually get corrected. Its failure mode is integral windup: if error stays positive the integral grows without bound and the controller saturates.
  • D — derivative. Responds to the rate of change, so it damps overshoot and reacts fast to a step change. Noisy signals make D dangerous.

What is being controlled here

Not traffic allocation. The controller widens the router's own uncertainty. The inner loop is ordinary Thompson sampling; the outer loop watches for a failure signature and responds by dividing both Beta parameters by an inflation factor:

alpha = successes / inflation
beta  = failures  / inflation

Dividing both preserves the posterior mean (α/(α+β) is unchanged) while increasing the variance. That is deliberate, controllable doubt: it adds uncertainty without biasing the estimate, so Thompson's draws spread out and it starts exploring again.

The signature, and the bug that shaped everything

The intuitive setpoint is max(posterior means): “if my best arm claims 96% and I am realising 71%, my model is stale.” That was the first implementation. It is wrong.

Trap

max over several noisy estimates is a biased estimator of the true maximum — it sits above it, always, because the arm that happens to be over-estimated is the one that wins the max. So the error term carried a permanent positive bias, the integrator wound up against it, and the controller sat at inflation ≈ 4 forever. Measured median inflation was 4.15 where it should have been 1.0 — a router that over-explores permanently and pays for it in conversion. (This is the “winner's curse” / maximisation bias, the same phenomenon Double Q-learning exists to fix in RL. Naming that connection lands very well.)

The fix — a calibration residual

# select(): record what we predicted for the arm we chose
self._pending_prediction = float(self.counts.mean[gateway])

# update(): score that prediction against reality
error = EWMA(predicted) - EWMA(observed)

Averaged over transactions, this difference is zero whenever the posterior is well calibrated — regardless of which arms were chosen or how many there are. So the controller idles at inflation 1.0 and costs nothing until the model is genuinely wrong. Two properties follow from choosing an unbiased residual, and both are worth more than the performance number:

  • It is silent during network-wide degradation. If every gateway drops together, predictions fall with outcomes, the residual stays near zero, and no exploration fires. A target-SR controller would do the opposite — spraying traffic across a failing network at exactly the wrong moment.
  • It is self-tuning across merchants. There is no per-merchant constant, because the setpoint is derived from the router's own forecasts.

The guardrails

GuardValueWhy
Integral clamp±2.0Anti-windup. Bounds how far the integrator can run against a persistent error.
Inflation clamp[1, 25]Lower bound is 1, so the controller can only ever add doubt. A negative u would sharpen the posterior beyond what evidence supports — which is how a router talks itself into a stale arm.
Warm-up hold50 obsCold-start noise would otherwise slam the integrator before either EWMA means anything.

The verdict — reported honestly

The controller does not beat a correctly tuned γ. Stacking both slightly over-explores. What it does do: against an untuned posterior it is worth +74 to +80 bps, it beats a badly set γ at both volumes, and it recovers roughly 60% of the gap to a perfectly tuned γ with no tuning at all.

Say this in the room

“The honest summary is one sentence: if you can tune γ per merchant and keep it tuned as volume changes, do that. If you cannot, the controller is the better default. It is not a better bandit — it is a way to avoid a per-merchant tuning problem that scales with merchant count.”

Rejected alternative worth naming

Change-point detection (CUSUM, Bayesian online changepoint) is sharper at catching the PG-Bravo outage. It was rejected because it requires a detection threshold — which is the same per-merchant tuning problem the controller exists to avoid. Being able to reject an alternative for a reason that is consistent with the rest of your design is a very strong signal in a design interview.

CHAPTER 07

Contextual bandits and partial pooling

Context is not free. This chapter is applied hierarchical Bayes, and it is very interviewable.

The cost of context

A flat bandit over 5 gateways tracks 5 posteriors. Conditioning on 5 issuers tracks 25, so every cell sees roughly a fifth of the traffic. Statistical power per cell drops with it, and a naive contextual bandit is therefore worse than a flat one until volume catches up — it has fragmented its evidence in exchange for resolution it cannot yet support.

This generalises badly. Real context is card network × issuer × amount band × merchant category. Five issuers is 25 cells; add four card networks and six amount bands and you are at 600 before you have said the word “merchant”. That combinatorial blow-up is one of the three defences of the agent layer in chapter 14.

Partial pooling — the fix

Do not choose between the two. Shrink each cell's posterior toward its gateway's pooled posterior:

alpha = k · m_g + successes[g, i]
beta  = k · (1 - m_g) + failures[g, i]

where m_g is gateway g's success rate across all issuers and k is a prior strength in pseudo-observations. A cell with no data of its own inherits the gateway's overall behaviour; as it accumulates evidence, that evidence takes over. k = 0 is pure contextual — maximum resolution, worst cold start. Larger k makes issuers look more alike.

Mechanism

This is hierarchical Bayes / James–Stein shrinkage under a different name, and it is the same idea as empirical-Bayes smoothing of batting averages or click-through rates. The interview-ready framing: “partial pooling lets you buy resolution incrementally rather than all at once. You pay for the resolution you have evidence for, and borrow strength from the parent for the resolution you do not.”

The cap — the sharpest detail in this file

strength = np.minimum(self.pooling, self.global_counts.total)
alpha = strength * pooled_mean
beta  = strength * (1.0 - pooled_mean)

The prior strength is capped by the pooled evidence that actually exists. Without that cap, a gateway nobody has tried yet gets a full-strength prior at its uninformative 0.5 mean — at pooling=40 that is Beta(20, 20), which is confidently mediocre and can never out-sample an arm with real evidence behind it. The result is a router that locks onto whichever gateway it happened to try first and never explores again. Capping by pooled evidence makes an unplayed gateway's prior Beta(1,1) — uniform, which explores.

The principle, stated in the docstring: never be more certain about a cell than the data backing its shrinkage target supports.

One honest consequence, documented rather than hidden: because the strength is capped, raising k past that ceiling changes nothing, so this does not interpolate all the way back to a flat bandit. Measured at k=100,000 on a 20k run, the broken cell still separates from its neighbours by ~6 percentage points. Bounded shrinkage in exchange for a router that does not lock on.

Per-issuer independent decay

The implementation stores one DiscountedCounts per issuer rather than one 2-D array. That keeps the per-issuer decay independent — an issuer with little traffic should not have its evidence aged out by transactions belonging to a busier one. If you stored a single array and decayed on every update, a low-volume issuer's cell would be forgotten at the fleet's rate, not its own. This is a genuinely subtle correctness point and it is worth volunteering.

Trap

The cell counts are constructed with prior=0.0, not 1.0. That is correct here — the prior mass comes from the pooled term, so adding another would double-count it. But it means the raw cell posterior alone is degenerate, which is exactly why _posterior ends with np.maximum(alpha, 1e-3): with pooling=0 and an empty cell both parameters would be zero and rng.beta would raise.

Realised SR hides everything interesting. These are the metrics that expose it.

Two implementation details with teeth

outage_response_ticks converts units. RunResult is indexed by transaction; a DegradationEvent is expressed in ticks. The function converts the window into transaction space with tx_per_tick before scanning. Mixing those two index spaces is the most likely silent bug in any simulation like this, and the code is explicit about it.

_rolling_mean is a prefix-sum, left-padded. csum[idx+1] − csum[lo] over a variable-width leading window, so the output aligns with the input and early entries are averaged over what exists rather than over zeros. A naive convolve would silently bias the first window entries toward zero and make every router look bad at the start.

Reproducibility as an engineering discipline

This is the part most portfolio projects skip, and it is a genuine differentiator. The constraint layer added two parameters to Router.select(). Every implementation early-returns on the original code path when blocked is empty, so random-number consumption is byte-identical to before those parameters existed. Why it matters: the benchmark numbers were measured before constraints existed. Change RNG consumption on the unblocked path and every published number becomes a lie.

It is enforced three ways: a test (test_unconstrained_selection_is_unchanged_by_the_new_parameters), a documented invariant, and a CI step that prints the numbers and asserts (realised_sr, total_regret) == (0.94916, 532.5) with an error message pointing at the invariant. Surfacing the actual values in the log means a reviewer can see reproducibility holds without digging through pytest output.

Mechanism

Look at EpsilonGreedyRouter.select: explore = self.rng.random() < self.epsilon is computed before the branch on blocked, so the same single draw is consumed either way. That is the discipline in miniature — the branch changes what happens, never how much randomness is spent getting there.

The model layer

Everything the Claude API does for you, and the four things it does not.

src/agent/llm.py puts two providers behind one Protocol. The second is not a mock — it is a full deterministic investigation policy. Start with the interface, because it is what makes the whole layer testable:

class LLMClient(Protocol):
    name: str
    def create(self, system: str,
                     messages: list[dict],
                     tools: list[dict]) -> LLMResponse: ...

Three arguments, one return type. Everything provider-specific — SDK objects, content blocks, usage accounting — is normalised into LLMResponse at the boundary. The loop above it never imports anthropic. That is why tests/test_agent_loop.py can drive every termination path with a 12-line ScriptedClient.

The API call, decision by decision

response = self.client.messages.create(
    model=self.model,                       # claude-opus-5
    max_tokens=self.max_tokens,
    system=[{"type": "text", "text": system,
             "cache_control": {"type": "ephemeral"}}],
    messages=messages,
    tools=tools,
    thinking={"type": "adaptive"},
    output_config={
        "effort": self.effort,
        "format": {"type": "json_schema", "schema": DIAGNOSIS_SCHEMA},
    },
)

1 · Tool definitions

A tool is a name, a description, and a JSON Schema for its arguments. The model does not execute anything — it emits a tool_use block containing a name and an arguments object, your code runs it, and you send back a tool_result block. The model never touches your system.

Every tool here is strict: true with additionalProperties: false. Strict mode means arguments are schema-valid before they reach your dispatcher — no missing gateway, no string where an integer belongs. What it does not guarantee is that the call is sensible: a valid call can still name a gateway that does not exist or invert a window. That is why the dispatcher returns a structured error rather than raising.

2 · Structured outputs

output_config.format with a json_schema constrains the model's final answer to match DIAGNOSIS_SCHEMA. This is grammar-constrained decoding: the sampler is restricted to tokens that can continue a valid document. The practical consequence is that the loop never has to salvage JSON out of prose — no regex for ```json fences, no bracket counting.

The schema is written out explicitly next to the dataclass it validates into, so the two cannot drift, and Diagnosis.from_payload re-validates anyway. Belt and braces on purpose: a refusal, a truncated stream, or the offline baseline can all produce something off-contract, and failing loudly there keeps a bad parse from being scored as a wrong answer, which would quietly corrupt the eval.

3 · Adaptive thinking

thinking={"type": "adaptive"} lets the model spend extended reasoning tokens before answering, scaled to the difficulty of the request. The justification given is task-specific and worth reusing: this is a diagnostic task with a real chance of reaching a confident wrong answer, and the reasoning is what stops the model from blaming the first gateway it looks at.

Trap

budget_tokens is removed on this model family and returns a 400. If an interviewer asks how you control thinking cost, the answer is output_config.effort, not a token budget.

4 · Prompt caching — the one that pays for itself

cache_control: {"type": "ephemeral"} on the system block marks a cache breakpoint. Everything up to and including that block is cached; subsequent requests with a byte-identical prefix read it instead of re-processing it. The ordering that matters:

tools  →  system  →  messages

Tools render before system, so a breakpoint on system covers both. And that is why two invariants exist:

  • Tool definitions are static and fixed-order. Any churn invalidates the prefix.
  • System prompts are static strings. No datetime.now(), no UUIDs, no per-incident interpolation. Volatile content goes in the user message via render_incident_brief.
Say this in the room

“A datetime.now() in a system prompt is my favourite example of a bug with no symptom. It does not crash, it does not fail a test, no assertion catches it — the cache hit rate silently drops to zero and your bill triples. The only defences are a convention that says system prompts are static, and a trace query that plots cache_read_input_tokens over time. The repo has both.”

5 · Refusals — check before you read

if response.stop_reason == "refusal":
    return LLMResponse(stop_reason="refusal", refusal_category=...)

A refusal is HTTP 200 with no usable content. Reading response.content first would either crash or produce an empty string that the loop then tries to parse as a diagnosis and records as an invalid_output — the wrong stop reason, so the wrong thing gets debugged.

6 · Errors are classified, not swallowed

APIStatusError is re-raised carrying its status code so the loop can distinguish a retryable outage from a request it must never send again; APIConnectionError becomes a distinct message. Both become RuntimeError, which the loop catches and turns into stop_reason="provider_error".

7 · Preflight

preflight() calls messages.count_tokens — same auth path, generates nothing, costs nothing. The reason it exists is a real failure that happened: an eval run with no key completes “successfully” with every case recorded as a provider error — 48 rows of zeros that look like a catastrophic quality regression rather than a missing environment variable.

The no-model baseline

BaselinePolicyClient implements the same create() signature and runs a fixed heuristic with no LLM at all:

fleet sweep → worst gateway → compare against a baseline window
            → segment by issuer if damage looks partial → conclude

It is a state machine over the transcript: it replays the tool results already in messages to work out what it has seen, exactly as the model would be reading them. Two thresholds encode its judgement: COLLAPSE_SR = 0.55 (below this a gateway is plainly dead rather than selectively broken) and HEALTHY_SR = 0.90.

Mechanism

An eval without a floor cannot tell you anything. If the model scores 0.82, the only useful question is “compared to what?” A hand-written heuristic is the honest comparison — and it means the loop, the dispatcher, the graders and the harness are all exercisable with no API key, which is what makes the eval suite CI-able. That last property is doing more work than it looks: the CI gate in this repo runs on every push with no secrets configured.

default_client() ties it together: live model when credentials exist and the SDK is importable, deterministic baseline otherwise, and the report says which one ran. A fresh clone works.

CHAPTER 10

The harness

The agent loop, line by line. This is the chapter to know cold — it is where the engineering is.

An agent loop is the simplest thing in the world to write and the hardest to make safe. The naive version is five lines:

while True:
    r = model(messages)
    if not r.tool_calls: return r.text
    messages += [r, run_tools(r.tool_calls)]

Every failure mode this project cares about is a branch that loop does not have. The SDK's tool_runner would write those branches for you; they were hand-written on purpose, because everything that actually pages someone lives in the parts it abstracts away: what happens when the budget runs out mid-investigation, when a tool errors three times in a row, when the model asks the same question twice, when the final answer does not parse.

The five guarantees

The budget

@dataclass
class LoopBudget:
    max_steps: int = 8
    max_tool_calls: int = 16
    max_output_tokens: int = 40_000
    wall_seconds: float = 300.0
    max_consecutive_tool_errors: int = 3
    repair_attempts: int = 1

Four independent ceilings, because they fail differently. Steps bound the reasoning depth. Tool calls bound the work — a model can issue several per step. Output tokens bound the spend. Wall seconds bound the latency, which the other three do not: a slow provider can blow your SLO inside two cheap steps. The docstring is explicit that these are “sized for this task, not universal truths.”

Answer-forcing — the design's best idea

stop = self._budget_exceeded(usage, elapsed, len(steps))
if stop and not forced:
    forced = True
    messages.append({"role": "user", "content": FORCE_ANSWER})
    stop = None                       # spend one more turn
elif stop:
    return self._finish(None, ..., "budget exhausted")

Rather than bailing the moment a budget trips, the loop spends one final turn demanding an answer. The FORCE_ANSWER message tells the model it has no budget left, forbids further tool calls, and instructs it to set confidence to reflect how little it was able to check. So budget exhaustion degrades to a low-confidence diagnosis rather than to nothing — and because from_diagnosis gates on confidence, a rushed answer is automatically less likely to move production traffic. Two mechanisms composing correctly.

The forced flag is also checked at the tool branch (if response.tool_calls and not forced), so a model that ignores the instruction and calls a tool anyway has its call dropped and its text parsed. There is no way to loop after forcing.

Duplicate suppression

signature = f"{pending.name}:{json.dumps(pending.input, sort_keys=True)}"
if signature in seen_calls:
    call = ToolCall(..., result={"note": DUPLICATE_NUDGE...}, is_error=False)
else:
    seen_calls.add(signature)
    call = self.dispatcher.dispatch(pending.name, pending.input)

sort_keys=True matters — {"a":1,"b":2} and {"b":2,"a":1} are the same call and must hash the same. The nudge tells the model it already made that call and to re-read the result above rather than repeating it. Note it is marked is_error=False: a duplicate is not a failure, it is a redirection.

The interaction found by testing, not design

Trap — expect to be asked about this one

Duplicate suppression pre-empts the error circuit breaker. If the model repeats the same failing call, dedup fires first and returns a nudge, so the tool never re-runs, so consecutive_errors resets to 0 and tool_error_limit never trips. The loop still terminates — via the step budget instead. Both paths are bounded, but only one of them is the one you would guess. There is a test named test_identical_failing_call_is_deduplicated_rather_than_counted that documents it, asserting tool_errors == 1 (only the first actually ran) and stop_reason != "tool_error_limit".

The right way to present this: “I found a real interaction between two safety mechanisms. I chose to document it with a test rather than 'fix' it, because both paths are bounded and reordering the checks would make a repeated bad call burn three real tool invocations instead of one. If I wanted the error limit to fire, I would count duplicates of a call that errored as errors — but that trades a wasted budget for a clearer stop reason, and the stop reason is only for me.”

The repair path

try:
    diagnosis = Diagnosis.from_json(response.text)
except DiagnosisFormatError as exc:
    if repairs_used < self.budget.repair_attempts and not forced:
        repairs_used += 1
        messages.append(self._assistant_turn(response))
        messages.append({"role":"user","content": REPAIR_NUDGE.format(error=exc)})
        continue
    return self._finish(None, ..., "invalid_output", str(exc))

One repair attempt, and the nudge carries the actual parse error so the model knows what to fix. and not forced prevents a repair-after-force loop. Two tests cover both outcomes: test_repair_attempt_can_succeed and test_unparseable_output_triggers_one_repair_then_gives_up.

Parallel tool results go back in ONE message

messages.append({"role": "user", "content": results})   # a LIST of tool_result blocks

The comment states the reason precisely: splitting them across several messages teaches the model to stop issuing parallel calls. The model learns from the conversation shape, and a transcript where parallel calls came back fragmented is a transcript that discourages parallelism — which costs you latency on every subsequent investigation. There is a test asserting exactly one tool-result message containing both blocks.

The n_steps parameter, and why it is passed in

A one-line bug that would have disabled the most important ceiling in the system, silently. Worth memorising as an example of “the comment that records why, not what”.

The dispatcher never raises

try:
    payload = self._invoke(name, arguments); is_error = False
except (KeyError, ValueError, TypeError) as exc:
    payload = {"error": str(exc)};           is_error = True

A tool error is a normal event in an agent loop — the model reads the message and corrects itself. So errors come back as content with is_error set, and the loop counts them. Note the error messages are written for the model: "unknown gateway 'PG-Foxtrot'; valid: PG-Alpha, PG-Bravo, ..." enumerates the options, so a recovery is possible on the next turn. An error message that just says “KeyError” burns a step.

Telemetry — the observable surface

TelemetryStore is the wall between the agent and ground truth. It exposes only counts of transactions that were routed and their outcomes. Two design details:

MIN_SAMPLES_FOR_SR = 30. Below 30 transactions, _sr() returns None rather than a number. Tools returning null is correct behaviour, not a bug to paper over — and the response includes a note explaining that the router may have already shifted traffic away. This forces the agent to reason about survivorship, not just read a number off a dashboard. It is also the direct cause of the volume dependence in chapter 13.

format_clock. Ticks are rendered as day 3, 14:05 in every response. A model reasoning about a diurnal pattern needs to know it is looking at midnight, and “minute 4320” does not say that. Small, and it is the difference between solving diurnal_trough and failing it.

Prompts — append-only versions

V1 = Prompt(version="v1-baseline", ...)   # role + output contract, nothing else

Never edit V1 or V2 in place — add V3 and change the default. v1-baseline is deliberately naive and is the control arm; “improving” it destroys the ability to show that prompt work bought anything. Prompts are the most-edited and least-tracked part of an LLM system; keeping them as immutable named versions in source makes a prompt change a reviewable diff, lets the harness run two head to head, and lets a regression be attributed to the edit that caused it.

V2's content is worth reading as a template. It has three sections — Procedure (an ordered investigation, “do not skip to a conclusion from the first tool result”), Traps (the three failure modes that produced every wrong answer under V1), and Reporting (that no_incident is a valid and useful answer). The traps are the part that generalises: a null success rate is not a healthy success rate; do not blame the gateway you looked at first; only cite numbers you actually observed.

Memory — two tiers, and why they differ

TierAnswersWhere it comes from
EpisodicWhat happened in one past incident.Written after each completed investigation.
SemanticWhat repetition has taught us — “PG-Bravo has degraded three times, always overnight.”Derived by consolidate(). No single episode contains it.

consolidate() groups episodes by (scope, gateway, issuer), promotes any group with min_support ≥ 2 into a RECURRING: semantic memory, and — crucially — rebuilds from scratch each call rather than updating incrementally, so a semantic memory can never outlive the episodes that justified it.

Retrieval is lexical, on purpose

IDF-weighted term overlap, plus a boost for semantic memories scaled by their support, plus a mild recency factor. No embeddings. The reason is experimental hygiene, not laziness:

Say this in the room

“A vector database would retrieve better. It would also make ‘does memory help?’ inseparable from ‘is this embedding model good?’, and the memory A/B exists to answer the first question. Swapping in vectors later changes _score and nothing else — the interface is recall(query, k).”

Memory is injected, not a tool

Recalled memories go into the user message via render_incident_brief, not exposed as a search_memory tool. Both designs work. Injection was chosen because it makes memory a clean on/off variable for the eval harness — with a tool, “memory helped” and “the agent chose to use memory” are confounded and the A/B stops answering the question it was built to ask.

Memories are labelled untrusted

# Recalled from previous investigations
These are prior findings from this fleet, retrieved automatically. They are
hypotheses to check against the telemetry, not established facts about the
current incident -- confirm or reject each with tools before relying on it.

A memory is a claim written by a previous run of a fallible agent. Treating it as established fact is how one early wrong diagnosis becomes permanent — the agent equivalent of a poisoned cache. Memories also record confirmed / later found incorrect / unverified, because an agent that only remembers its confirmed wins learns nothing from its mistakes.

Configuration and secrets

config.py resolves every tunable from the environment, with a 30-line .env loader instead of a python-dotenv dependency. Real environment variables always win over .env, so a deployed secret is never shadowed by a stale checked-out file. Two rules carry weight:

  • Every default reproduces the measured behaviour. If an unset variable changed a default, the published numbers would depend on the shell they were run in. There is a test — test_defaults_reproduce_the_measured_behaviour.
  • Secrets never leave the environment. redact_dsn reduces a connection string to <redacted>@host:port/db, and Settings.describe() exists precisely so a run can log its own config safely. Three tests assert a known password never appears in describe(), TraceStore.target, or stats().

Tracing — and the rule that governs every sink in this repo

The story that sells the whole project

Say this in the room

“The first version had six cases. The deterministic baseline policy — a fixed heuristic with no model at all — scored 100%. That is not a good result, it is a broken eval. That test is test_baseline_policy_scores_below_ceiling_and_above_floor, and the invariant is stated as a rule: if it fails at 1.0, add harder cases; do not relax the test. A saturated eval is worse than no eval, because it produces a green light with no information in it.

Telemetry generation — a subtle, important choice

The eval telemetry is generated with ε-greedy at ε=0.25 and 300k transactions, not with the benchmark's winning router. The reason:

Every case must be answerable. The hard cases turn on comparing one issuer's SR against the others on the same gateway, which needs enough traffic in every gateway×issuer cell to compute a rate at all. Under the benchmark's winner the affected gateway drew ~120 transactions in the window, so four of five issuer segments came back null and the case could not be solved by any agent, however good. Raising volume and exploration puts every cell above the sampling floor. The router still adapts, so get_traffic_shift still shows it pulling away — the survivorship signal survives, it just no longer censors the evidence.

Mechanism

This is a general principle for eval design: an unanswerable case measures nothing. If the information required for the correct answer is not present in what the system can observe, you are measuring luck. Diagnosing that — and fixing the data generator rather than the grader — is the kind of thing that separates someone who has built an eval from someone who has read about one.

Caching, and the invariant that protects it

Generating six weeks of telemetry takes ~100 s, long enough to discourage running the eval — and an eval you avoid running is an eval that stops catching regressions. Results are deterministic given the seed, so they cache to results/eval_cache/*.npz and later runs start instantly.

The danger is obvious once stated: stale telemetry graded against new ground truth. Two defences. CACHE_VERSION is baked into the filename and must be bumped when anything shaping telemetry changes. And in CI the cache key is hashFiles('src/agent/evals/cases.py','src/gateways.py','src/simulator.py','src/routers/*.py','src/metrics.py') — every file that determines the telemetry.

Grading: deterministic first, judge only where determinism cannot reach

MetricWhat it catches

partial_credit0.5 scope / 0.3 gateway / 0.2 issuer, so progress shows while exact_match is still 0.

Brier is the one to lead with. Confidently wrong is the expensive failure in an on-call context — it is what gets a good gateway drained during an incident — and Brier is the metric that names it. Note that a failed run leaves confidence at 0.0 deliberately, so an investigation that produced nothing is scored as maximally wrong and maximally unconfident, which keeps Brier honest.

segmentation_rate is the one to mention second, because process metrics are rare and they catch a real failure: an agent that reaches the right answer without doing the work is one distribution shift away from being wrong, and outcome metrics cannot see that.

The LLM judge, and its stated limits

Scope, gateway and issuer are known exactly, so grading them with a model would be strictly worse — slower, more expensive, less reliable than ==. The judge is reserved for the one thing with no ground truth: whether the written summary would help the engineer who got paged. Three rubric dimensions (actionability, groundedness, overclaiming), scored 1–5, reported in separate columns so a fluent wrong answer can never inflate the headline. Its known limits are documented in the class docstring rather than discovered later: it sees ground truth so it is not blind, it is not calibrated against human raters, and it scores prose rather than correctness.

Arms, and measuring memory on recurrence

An arm is one configuration: provider × prompt version × memory on/off. Each arm runs the case set twice with one MemoryStore persisting between passes, and consolidate() runs between them. The first pass is cold; by the second, the store holds episodes and any derived pattern. If memory is worth anything, pass 2 should be cheaper (fewer tool calls to the same answer) or more accurate. Measuring memory on a single cold pass would measure nothing, since there would be nothing to remember.

The gate

    regressions.append(f"{m.arm} pass {m.pass_index}: {was:.3f} -> {m.exact_match:.3f}")

CHAPTER 13

Closing the loop

Where a language model's output moves real money. The most paranoid code in the repo.

The problem a flat bandit cannot express

PG-Delta is the fleet's best gateway at 94.5%, so the router sends it most of the traffic. It starts declining HDFC cards almost entirely. Everyone else still converts on it at 94%.

A flat bandit tracks one number per gateway. All it can see is PG-Delta's aggregate SR falling, and its only available response is to route away from PG-Delta — for everyone. It fixes HDFC by taking the fleet's best gateway away from the 69% of traffic that was converting on it perfectly.

The closed loop can express what is actually true: avoid PG-Delta for HDFC, and leave everyone else where they are. That is the entire reason RoutingContext is threaded through Router.select() even though every strategy in the package ignores it.

The gate: from_diagnosis

if diagnosis.scope not in ACTIONABLE_SCOPES:      return None  # fleet_wide, no_incident
if diagnosis.confidence < min_confidence:         return None  # default 0.6
if not diagnosis.primary_gateway:                 return None
if diagnosis.primary_gateway not in fleet_names:  return None  # hallucinated name
if scope == "issuer_specific" and not affected_issuer: return None
Say this in the room

“Declining is the common case and the important one. A diagnosis is not an instruction. This function is the gate between ‘a language model said something’ and ‘the system moved production traffic’, and returning None is the safe default. The last check is the final barrier against a hallucinated gateway name — most of test_constraints.py tests what this layer must refuse to do, not what it does.”

Note why fleet_wide is refused rather than acted on: it names no culprit. Everything is degraded, so steering traffic between gateways cannot help — and blocking one gateway during a fleet-wide event just concentrates traffic onto the survivors, making things worse. The refusal is a correctness argument, not caution.

Three properties that keep it safe

Scoped, not blunt

An issuer_specific diagnosis produces a constraint with issuer set, and RoutingConstraint.matches() compares case-insensitively against the transaction's issuer. A single_gateway diagnosis produces issuer=None, which matches everything.

Never a total block — the canary

if self.rng.random() < constraint.canary_rate:   # default 2%
    self.canary_releases += 1
    continue                                     # let this one through

Without it, a blocked gateway stops producing observations, its posterior freezes, and nothing can ever justify lifting the constraint — the system would have made itself permanently blind. That is the same survivorship trap the router already fights, now self-inflicted. Canary outcomes flow into the posterior exactly like any other, which is what lets the bandit notice recovery on its own.

Always expiring — the TTL

Default 480 minutes. A constraint written during an incident is evidence about the past, and gateways recover. When it expires traffic returns; if the problem is still live, the next investigation re-applies it. An immortal constraint is a permanent capacity cut based on a six-hour-old observation.

Plus a safety interlock

if len(blocked) >= len(self.fleet_names):
    return frozenset()      # honour none rather than strand the transaction

If honouring every constraint would leave a transaction with nowhere to go, none are applied. A transaction that reaches no gateway is a guaranteed failure, which is strictly worse than one routed to a suspect gateway. The same idea appears in every router's select: an all-blocked set falls back rather than raising.

Composition, not a new strategy

class ConstrainedRouter:
    def select(self, tick, context=None, blocked=frozenset()):
        context = context or RoutingContext(tick=tick)
        learned = self.store.blocked(context)
        return self.inner.select(tick, context, blocked | learned)

One wrapper works with all six strategies rather than five near-duplicate subclasses. The bandit keeps doing what it does well — tracking which gateway converts best — and the constraint layer supplies the one thing it structurally cannot know.

No lookahead — how the measurement stays honest

telemetry = TelemetryStore(
    _partial_result(specs, chosen, success, latency, ticks, issuers, i), specs
)

At a detection tick, the simulation pauses and hands the agent a RunResult truncated at index i — the transaction currently being routed. The agent cannot observe a transaction that had not happened yet. There is a test named test_agent_sees_no_data_from_after_the_detection_point. Without that truncation, the whole closed-loop measurement would be circular.

  1. Detection lag. The constraint lands 60 minutes in. The flat bandit has already spent that hour souring on PG-Delta for everyone.
  2. The constraint stops the bleeding but does not repair the damage. Mechanism

Point 2 is a real insight about the architecture, not an excuse. A constraint is a filter on the action; it does nothing to the belief. The obvious follow-up design — and a great thing to volunteer as “what I'd do next” — is to have the constraint also quarantine or roll back the posterior evidence attributable to the diagnosed path. That is a harder change (you need per-context attribution of past outcomes, which is a contextual bandit again in disguise), and naming that tension shows you followed the argument to its end.

Where the agent's value actually is

Do not defend the agent on the metric it lost. Move the argument:

  • It handles failures nobody enumerated as a dimension. A fleet-wide event, or a diurnal trough mistaken for an incident — a bandit has no cell for those. Two of the eight eval cases are exactly this shape, and no contextual bandit over issuers can express either.
  • It produces an explanation a human can act on. A posterior cannot say “PG-Delta is declining HDFC traffic at 9.49% while other issuers convert near 93.33%”, and that sentence is what gets a ticket raised with the provider. The bandit fixes the symptom silently; nobody ever calls PG-Delta.
  • It does not pay the dimensionality cost. Five issuers is 25 cells. Card network × issuer × amount band × merchant category is hundreds to thousands, and per-cell evidence collapses. The agent's cost is one investigation, independent of how many dimensions the failure lives on.
Say this in the room

“The strongest version of this system is both: a contextual bandit for the axes you know about, an agent for the ones you do not. The bandit is a cheap, fast, always-on response to enumerable failure modes. The agent is the thing you page when something happens that nobody put a dimension in for. And the repo says so — AGENTS.md has a rule that this finding must not be quietly reversed, and that if the ordering ever flips, the reversal has to come with an explanation of which mechanism changed.”

CHAPTER 15

Off-policy evaluation

How you decide whether a new policy is better without routing real payments through it.

The deployment question

You have logs from the policy in production. You have a candidate. You want to know whether the candidate is better before routing real payments through it, because the alternative is an A/B test that costs declined transactions to run.

The core object: the propensity

π_logging(a | x) — the probability the logging policy assigned to the action it actually took. This is the field nobody logs until it is too late. Without it none of the estimators are computable and your logs are only good for measuring the policy that produced them. In this repo it is recorded at decision time, carried in the routing response, written onto every RoutingEvent, and shipped to ClickHouse.

Four estimators, in increasing order of assumption

IPS — inverse propensity scoring

w_i   = π_target(a_i | x_i) / π_logging(a_i | x_i)
V_IPS = mean(w_i * r_i)

Reweight logged rewards by how much more (or less) the target policy would have taken that action. Unbiased, and often uselessly noisy: one transaction with a small logging propensity can dominate the entire estimate.

SNIPS — self-normalised IPS

V_SNIPS = sum(w_i * r_i) / sum(w_i)

Divide by the summed weights instead of n. Slightly biased, dramatically lower variance, and — the property that matters — it cannot return a value outside the range of observed rewards. Its standard error uses the delta method for a ratio estimator, which is why the code computes sqrt(sum((w·(r−V))²)) / sum(w) rather than a naive standard deviation.

DM — direct method

Fit a reward model r̂(x, a) from the logs, then average its predictions under the target policy. Low variance, biased by exactly however wrong the model is, and it fails silently where the logs are thin. Here the model is non-parametric — an empirical cell mean per (issuer, gateway), because the context is a five-valued categorical and a cell mean is the correct model.

DR — doubly robust

V_DR = mean( Σ_a π_target(a|x)·r̂(x,a)  +  w_i · (r_i − r̂(x_i, a_i)) )

DM plus an importance-weighted correction on the model's residuals. Consistent if either the reward model or the propensities are right — hence “doubly robust”, and hence the default in practice. Reference: Dudík, Langford & Li (2011).

Cross-fitting

_cross_fit fits the reward model out-of-fold. Fitting on the same rows it then scores biases DM and DR toward the logging policy's own choices — the model has memorised the actions it is being asked to evaluate. Three lines to remove it, and it is the sort of detail that signals you have actually used these estimators.

  • IPS returns success rates above 100%. Rewards are 0/1, so 1.9476 is not merely wrong, it is incoherent — and nothing in the estimator prevents it. Unbiased and useless at the same time.
  • ESS decides whether an estimate means anything. With 11,790 effective samples every estimator lands within 15 bps. With 119, IPS is off by 100 percentage points. Same 40,000 rows.

Say this in the room

“The practical rule the numbers support: ship SNIPS or DR, always report ESS alongside, and treat a candidate far from the logging policy as unevaluable rather than as evaluated-badly. Off-policy evaluation is interpolation, not extrapolation — it cannot tell you about actions nobody ever took.”

Why this module can be validated at all

OPE is normally unfalsifiable in the moment: you produce an estimate and find out years later whether it was any good. Here the environment is a simulator, so the true value is computable in closed form — V(π) = (1/n) Σᵢ Σₐ π(a|xᵢ)·true_sr[a, tᵢ, xᵢ]. That makes every estimate checkable against the answer, which is the only honest way to claim an estimator works. Building OPE without that validation step is taking it on faith.

The two assumptions that bite

  • Positivity / overlap. The logging policy must assign positive probability to every action the target might take. LoggedData.__post_init__ raises if any propensity is ≤ 0, with an error message that explains why. _empirical_support computes the fraction of rows where the target wants an action the logger never took in that context — pure extrapolation.
  • Both policies are frozen. This is not a simplification, it is a requirement. Importance sampling asks “what if this same decision had been made differently”; it cannot answer “what if a learning policy had seen different data and therefore been in a different state at every subsequent step”. Evaluating an adaptive learner offline needs counterfactual histories, which logs do not contain. Freeze the candidate, evaluate the frozen thing, then deploy it and let it learn.

And the constraint from chapter 4, restated because it is the one people miss: you cannot do OPE from a deterministic logging policy. If you want to evaluate policies offline later, what you deploy today has to be stochastic. This is an argument for Thompson sampling that has nothing to do with regret.

LangChain, LCEL, and why this project has none

You will be asked. Know the framework better than someone who only uses it.

Get this straight first

This project does not use LangChain. It uses LangSmith (optional hosted prompt storage) and Langfuse (optional trace tree storage), which are observability and prompt-management products, not the orchestration framework. The agent orchestration is hand-written in src/agent/loop.py. Saying “I used LangChain” would be wrong; saying “I evaluated it and chose not to, here is why” is the answer that scores.

The Runnable — the one abstraction

Everything in modern LangChain is a Runnable: an object with a uniform interface.

.invoke(input)          # one input  -> one output
.batch([i1, i2, ...])   # many inputs, parallelised
.stream(input)          # yields chunks as they arrive
.ainvoke / .abatch / .astream    # async variants

Prompt templates, chat models, output parsers, retrievers, and plain functions are all Runnables. Because they share one interface, they compose.

The pipe operator

chain = prompt | model | StrOutputParser()
chain.invoke({"topic": "payments"})

| is Python's __or__, overloaded on Runnable. a | b returns a RunnableSequence(first=a, last=b). It is not magic and it is not a DSL parser — it is operator overloading, exactly like pathlib's /. The mental model is the Unix pipe: the output of the left becomes the input of the right.

Two conveniences follow from __or__ plus __ror__:

  • A bare function is coerced. chain | (lambda x: x.upper()) wraps the lambda in a RunnableLambda automatically.
  • A bare dict is coerced too, into a RunnableParallel.

The distinction that matters: a chain is a DAG, an agent is a loop

Mechanism

A chain is a directed acyclic graph. Data flows forward, the shape is known before you run it, and it terminates because there are no cycles. An agent is a loop with a model-controlled exit condition: the model decides whether to call another tool or stop, so the number of iterations is not known in advance and termination is not structural — it is something you have to engineer. That is the whole reason chapter 10 exists. You cannot express “stop after 8 steps, but spend the last one forcing an answer, and dedupe identical calls, and give up after 3 consecutive distinct tool errors” as a pipe.

LangGraph is LangChain's answer: a state machine where you declare nodes, edges, and conditional edges over a typed State, with checkpointing, interrupts, and recursion_limit as a global step cap. It is genuinely the right tool for many agents. The map onto this repo would be: State = {messages, steps, usage, seen_calls}, nodes call_model and execute_tools, a conditional edge on “did the response contain tool calls”, and the budget checks as edge predicates.

Why this project hand-wrote it anyway

The argument is narrow and defensible, and it is the same argument the README makes about prometheus_client, matplotlib, and pydantic:

  • The abstracted parts are the interesting parts. Budget exhaustion mid-investigation, repeated tool errors, a duplicated call, an unparseable final answer. Those are the branches under test in tests/test_agent_loop.py — and behind a framework they are someone else's branches, tested by someone else's tests, changed by someone else's release.
  • The dependency budget. The core library's only runtime dependency is numpy, which is what makes the eval suite CI-able with no secrets and no lockfile drift. langchain-core alone pulls in pydantic, typing-extensions, jsonpatch, PyYAML, tenacity and more.
  • It is 250 lines. The loop, budgets, dedup, repair and forcing fit in one readable file with a docstring that states five guarantees.

There is even a small, concrete instance of the trade in the repo: prompt_source.py avoids client.pull_prompt() — which returns a LangChain ChatPromptTemplate and therefore drags in langchain-core — and uses pull_prompt_commit() instead, walking the raw manifest to extract the template text with no extra dependency.

Say this in the room — the balanced answer

“LangChain is the right default for most agents, and I'd reach for LangGraph on a team where several people need to modify the orchestration and the value is in shipping fast. I skipped it here for two specific reasons. First, the failure modes I wanted to own — budget exhaustion, tool-error circuit breaking, duplicate suppression, output repair — are precisely what the framework abstracts, and they are what pages someone at 3am. Second, the numpy-only dependency floor is what lets the whole eval suite run in CI with no secrets. I did keep the two pieces of the ecosystem that solve problems I did not want to solve: LangSmith for hosted prompt management and Langfuse for trace trees — and I documented the cost of the first, which is that a prompt editable outside git means the eval gate no longer gates the prompt that ran.”

Where the two hosted products actually sit

LangSmith (prompt_source.py) lets someone edit a prompt without a deploy and without opening a pull request — a real need on a real team. The cost is stated rather than glossed: CI green on a commit stops implying “this prompt scores 75%” and starts implying “some prompt did, once.” Three things keep it honest — AGENT_PROMPT_COMMIT pins an exact commit; the resolved source, identifier and commit hash go onto every trace; and no credentials, no network, or an unknown name all fall back to the git registry rather than failing. Offline reproducibility is not negotiable, so resolution fails open. Results are also cached in process, because pulling over the network on every investigation would put a third-party outage on the incident-response path.

Langfuse was chosen over LangSmith for tracing for one reason: it self-hosts. Payment telemetry under RBI localisation cannot go to a SaaS-only endpoint, and LANGFUSE_HOST is a one-line change. Token usage is attached to a generation observation so Langfuse's own cost tracking works rather than being duplicated as invented metadata.

CHAPTER 18

The Haskell DSL

Making invalid states unrepresentable — the smallest chapter, the highest signal-per-line.

What it is

avoid PG-Delta when issuer HDFC ttl 8h canary 2% confidence 0.70
avoid PG-Bravo ttl 30m canary 5% confidence 0.85
routing-dsl check   constraints.route   # non-zero exit on the first bad line
routing-dsl compile constraints.route   # emits JSON the Python router consumes

A tiny language for routing constraints, with a parser, a validator and a CLI, in base-only Haskell. The pipeline is text → AST → validated constraint → JSON. Haskell owns the grammar and the invariants; Python owns the hot path.

The argument for its existence

Most of what from_diagnosis checks at runtime is expressible in a type. And where it must be checked, the check should happen once, at parse time, not on every routing decision.

Sum types carry their payload

data Scope
  = SingleGateway Gateway
  | IssuerScoped  Gateway Issuer

IssuerScoped requires an issuer. There is no way to construct an issuer-scoped constraint without one. In Python that is a runtime check (if scope == "issuer_specific" and not affected_issuer: return None); in Haskell it is a compile error. Likewise Gateway and Issuer are separate newtypes, so passing one where the other belongs — easy to do and silent when both are String — will not compile.

Smart constructors make bad values unrepresentable

newtype CanaryRate = CanaryRate Double     -- constructor NOT exported

mkCanaryRate :: Double -> Either ValidationError CanaryRate
mkCanaryRate r
  | r < 0     = Left (CanaryOutOfRange r)
  | r >= 1    = Left (CanaryOutOfRange r)
  | otherwise = Right (CanaryRate r)

The module exports the type but not the constructor, so the only way to get a CanaryRate is through mkCanaryRate. A rate outside [0, 1) is not rejected — it is not representable. Note it rejects exactly 1.0 too: a constraint that lets everything through is not a constraint.

Errors that teach

renderError ZeroCanaryWithoutOverride =
  "canary rate 0 makes the blocked gateway permanently unobservable, so the
   constraint could never be retired on evidence; write `canary 0% unsafe`
   if that is genuinely intended"

The error text carries the reason — the same survivorship argument from chapter 13 — and names the escape hatch. A constraint language that said only “parse error” would be worse than the Python dataclass it replaces.

Defaults chosen for safety

parseCanary defaults to 2%, not 0. Omitting a field should give the safe behaviour, not the dangerous one — because 0 makes the blocked gateway permanently unobservable. Choosing the default that fails safe is a small decision that says a lot.

Why Haskell, and why base only

The job is a parser with invariants, which is what the language is for. Token-level recursive descent over words rather than megaparsec, and hand-rolled JSON rather than aeson, so the package builds with a bare GHC and can sit in CI with no package resolution. check exits non-zero on the first bad line, so it gates a build the same way the eval gate does — a constraint file that does not parse should fail the build, not reach the router.

Be honest about this one

The README states the verification status plainly: the library and CLI compile cleanly under -Wall on GHC 9.6 and were exercised end to end — the example validates, the JSON round-trips into the Python RoutingConstraint, an unknown gateway is rejected with a useful message — but the QuickCheck property suite in dsl/test/Spec.hs has not been run. If asked, say that. Volunteering an unverified corner costs you nothing and buys you credibility on everything else you claim.

The one design gap to acknowledge

knownGateways and knownIssuers are hardcoded in Main.hs, with a comment saying that in a deployment they would come from the router's /health. That is the right call for a CI gate with no runtime dependency, but it means the fleet definition now lives in two places and can drift. The clean version fetches the fleet at check time with the hardcoded list as a fallback, or generates the Haskell list from the Python fleet definition at build time.

CHAPTER 19

Design review — what is wrong

Read with a system-design hat on, here is what I would raise. Bring these yourself.

Nothing below is fixed in code — it is the review. Most of these only bite at multi-replica or production scale, which is exactly why they are worth raising: they show you can read your own work as a system rather than as a program. Order is roughly by severity.

1 · The Redis constraint TTL is in the wrong unit

Correctness
Where
service/state.py — RedisConstraintStore.add
What
ttl = max(1, expires_tick − created_tick) is in simulated minutes, then passed straight to setex(key, ttl, payload), which takes seconds. An 8-hour constraint (480 minutes) becomes a 480-second Redis key — eight minutes.
Effect
Invisible on one replica, because the local list is authoritative for its own constraints. On several replicas, peers stop seeing the constraint 60× earlier than it is actually in force. The comment (“in a real deployment the two clocks are the same clock”) papers over a unit mismatch that is real today.
Fix
setex(key, ttl_minutes * 60, payload), and make the tick unit explicit in the type — a Minutes newtype, or name the field expires_minute.

2 · Duplicate constraints silently destroy the canary

Safety invariant
Where
src/agent/constraints.py — ConstraintStore.add / blocked
What
add() always appends; there is no dedup on (gateway, issuer). blocked() then rolls the canary once per constraint, and a gateway is released only if every matching constraint rolls through. With k duplicates the effective canary rate is r^k — at r = 2% and k = 2 that is 0.04%.
Effect
Calling /investigate twice for the same live incident — the obvious operator behaviour — collapses the canary to nothing. The blocked gateway stops producing observations, its posterior freezes, and the constraint can never be retired on evidence. That is precisely the failure the canary exists to prevent, reintroduced by a duplicate.
Fix
Deduplicate on (gateway, issuer) in add() — replace and extend the TTL rather than append. Then roll the canary once per decision, not once per constraint, so the rate is a property of the path rather than of how many rows happen to describe it.

3 · The tick is process-relative, and it is shared state

Distributed
Where
service/api.py — RouterService.tick
What
int((time.time() − self.started)/60) + clock_offset. Every replica's clock starts at zero when that replica started. But created_tick and expires_tick travel through Redis to peers, which compare them against their own local tick.
Effect
A replica that started three hours after its peer has tick ≈ 0 and evaluates constraint.active(tick) as created_tick <= 0 → false. The constraint silently does nothing on that replica. Restarting a pod resets its clock and un-applies every shared constraint it holds.
Fix
Use an absolute epoch-derived clock — int(time.time() // 60), Unix minutes — so every replica agrees. The demo's clock_offset stays as a test-only addend. Nothing else in the design changes.

4 · The agent reads one replica's memory, not the event store

Architecture
Where
service/api.py — /investigate builds TelemetryStore(svc.history(), ...)
What
The cold path reads the in-process history ring of whichever replica served the request. Meanwhile every outcome is already being published to Kafka and landing in ClickHouse — a columnar store built for exactly this query shape.
Effect
With N replicas the agent sees 1/N of the traffic, so the MIN_SAMPLES_FOR_SR = 30 floor bites N times harder and every gateway×issuer segment returns null. The volume dependence documented in chapter 13 gets N× worse for a reason unrelated to actual traffic. It is also non-deterministic: the same investigation returns a different answer depending on which pod answered.
Fix
Back TelemetryStore with a ClickHouse query behind the same six-method interface. The tools do not change, the loop does not change, the eval keeps using the in-memory implementation. This is the single largest architectural inconsistency in the repo — the event pipeline exists and the consumer that most needs it does not use it.

5 · Hot and cold paths share one thread pool

Isolation
Where
service/api.py — both /route and /investigate are def, not async def
What
FastAPI runs sync handlers in a bounded anyio thread pool (40 by default). /investigate blocks a worker for seconds on an HTTP call to a model provider.
Effect
The README's framing is latency (“an agent that is slow is fine”), but the real coupling is thread starvation. Forty concurrent investigations — or forty stuck ones behind a provider timeout — and /route has no worker to run on. The router does not get slower; it stops.
Fix
The stated end-state (separate service) is correct. Short of that: a bulkhead — run the investigation on its own bounded executor, or make the handler async and enqueue to a worker, so the cold path can only ever exhaust its own budget.

6 · One global lock, taken twice per decision

Concurrency
Where
service/api.py — RouterService._lock
What
A single threading.Lock guards router.decide(), router.update(), five history appends, and the decision counter — and route() acquires it twice, once for the draw and again for self.decisions += 1.
Effect
Every routing decision in the process is serialised. At ~35 µs that caps a single process at roughly 28k decisions/second no matter how many cores it has. Correct, but it means the service scales only by process count.
Fix
Fold the counter into the existing critical section (free). Then either run single-threaded workers and scale by process — which is the honest answer for CPython — or move the counts to per-arm atomics, since a Beta posterior tolerates a slightly stale read and the update is commutative.

7 · history() copies 200k rows under the routing lock

Performance
Where
service/api.py — history(), _append_history()
What
history() copies five Python lists of up to 200,000 elements while holding the lock /route needs — and /simulate/state, which the UI polls, calls it every time. Separately, the ring trim is del self._hist_tick[:drop], which is an O(n) memmove on every append past the cap.
Effect
A multi-millisecond hot-path stall per poll, on a path whose entire budget is microseconds. The p99 in the latency histogram would show it and the p50 would not.
Fix
Preallocated numpy ring buffers with a head index — O(1) append, no trim, and a snapshot that copies only the tail actually needed. Or a collections.deque(maxlen=…) as a one-line improvement over the list.

8 · The confidence gate trusts a self-reported number

Trust boundary
Where
src/agent/constraints.py — from_diagnosis
What
The gate between “a model said something” and “traffic moved” turns on diagnosis.confidence >= 0.6 — a field the model writes about itself. It is the least trustworthy value in the payload, and the eval's own Brier score exists precisely because models are badly calibrated.
Effect
An overconfident model walks straight through the gate. The other four checks are structural and hold; this one is decorative under exactly the failure it is meant to catch.
Fix
Verify the evidence server-side before installing. The diagnosis already cites numbers (“HDFC on PG-Delta: 9.49%”). Re-query the telemetry store for the claimed segment and require the gap to actually hold — a scoped constraint installs only if the named cell is genuinely below its peers by a margin, at above the sample floor. That converts an LLM assertion into a checked fact and makes the gate independent of the model's self-assessment. This is the highest-value change on the list.

9 · No kill switch and no install rate limit

Blast radius
What
There is no global “ignore all learned constraints” flag, and no cap on how many constraints can be installed per window. If the agent installs a bad one, the only remedies are TTL expiry — up to 8 hours — or a restart, which chapter 19 item 3 shows also drops peers' constraints.
Fix
A single Redis flag checked in ConstraintStore.blocked(), plus a cap (“at most N constraints active, at most M installed per hour”) and an alert on routing_constraints_active crossing a threshold. Any system that lets an automated component change production behaviour needs a switch a human can reach in one second.

10 · /simulate/* is mounted on the production app

Surface
What
app.include_router(demo_router). POST /simulate/reset replaces the live router — posterior, constraints, counters. /simulate/incident mutates the fleet. There is no auth, no rate limit and no idempotency key on any endpoint in the service.
Fix
Gate the demo router behind an explicit environment flag (default off), or mount it on a separate app and port. The docstring says “kept in its own module so it is obvious which endpoints are the demo” — module separation is documentation; a flag is enforcement.

11 · The propensity round-trips through the client

Data integrity
What
/route returns a propensity; the caller sends it back on /outcome and the service writes it to the event stream unchecked. Nothing verifies that the gateway reported is the one /route returned, or that the transaction id was ever issued.
Effect
The one field the entire off-policy evaluation depends on is supplied by an untrusted party. A buggy or malicious merchant integration silently corrupts every future policy estimate — and, per chapter 16's defect table, this is exactly the class of error that never surfaces as a crash.
Fix
Keep a short-TTL pending-decision record server-side keyed by transaction id, and join the outcome to it. The propensity, the context and the constraint set then come from the decision, not from the report.

12 · Posterior snapshots are last-writer-wins with no staleness check

Distributed
What
Every replica writes its full posterior to one key, route:posterior:snapshot, every 5 seconds, and restore() loads whatever is there with no age check.
Effect
Replicas clobber each other, so a restarting pod warms from an arbitrary peer's view. And a snapshot from three days ago restores as if current — with γ = 0.999 the counts saturate around 1,000 pseudo-observations, so a stale snapshot is a confident wrong prior that takes another 1,000 real transactions to wash out.
Fix
Per-replica keys plus a saved_at max-age (the field is already written and never read), and decay the restored counts by elapsed time before use. Refusing to restore is strictly better than restoring something stale.

13 · Smaller things worth naming

Assorted
Thread safety
ConstraintStore.blocked() is called outside the service lock and uses a shared numpy.random.Generator, which is not thread-safe; canary_releases += 1 is likewise unguarded. ClickHouseSink.buffer is appended from multiple threads with no lock.
ClickHouse
Batches flush at 500 rows with no time-based flush, so during a quiet period events sit in memory indefinitely and are lost on crash.
Redis refresh
scan_iter plus one GET per key, per replica, per second. Should be one MGET or a pipeline — or pub/sub invalidation instead of polling.
Prompt caching
Only the system block carries cache_control. The messages array grows with every step and is never marked, so each turn re-pays for the whole transcript including large JSON tool results — which dominate cost by step 6. A second breakpoint on the latest tool result would make caching incremental.
Retries
Any exception from client.create ends the investigation as provider_error. A single 429 or 529 kills a run that a short backoff would have saved.
Eval cost
aggregate() computes cost as total_tokens × (input_rate + output_rate)/2, which is only right at a 50/50 mix — and with a cached prefix and tool results the mix is nowhere near that. Usage.cost_usd() already does it correctly and is not used here.
Gate scope
check_gate skips arms absent from the baseline (if was is None: continue). Renaming an arm silently disables the gate for it — the same fail-open shape as the eval_baseline.json gitignore hazard.
Sample floor
MIN_SAMPLES_FOR_SR = 30 is a fixed count, not an interval. At n = 30 and p = 0.9 the 95% CI is roughly ±11 points — wide enough to look like an incident. Returning a Wilson interval alongside the rate would let the agent reason about overlap instead of comparing point estimates.

The canary rate, at scale — a design point rather than a defect

Mechanism

A canary expressed as a percentage means the number of deliberately-failed payments grows linearly with traffic. On a gateway declining 100% of HDFC, a 2% canary at 350M/day is an enormous absolute number of intentional failures, sustained for the full TTL. But the number of probes you need to detect recovery is roughly constant — a few dozen per minute is plenty. The right shape is a rate-limited canary: N probes per minute, or a small fixed QPS, not a proportion. Percentage-of-traffic is correct at demo scale and wrong at production scale, and noticing that a parameter's units are wrong for the deployment is a strong design-interview move.

CHAPTER 21

Questions and answers

Sixty questions, the answers, and how to handle the ones designed to knock you over.

Opening and framing

Walk me through the project.

Use the 90-second opening from chapter 1 verbatim. Three layers, the headline number, then volunteer both negative results. Stop and let them pick a thread — do not narrate all 21 chapters.

What was the hardest part?

“Designing an eval that could be wrong. My first version had six cases and a no-model heuristic scored 100% on it — which felt like success and was actually a broken instrument. Every case was solvable by ‘find the lowest success rate’, which is exactly what the heuristic encodes. I added two cases that invert a threshold rule and there is now a test that fails if the baseline ever returns to 100%.”

What would you do differently?

Pick from chapter 19 and lead with #8: “I'd make the constraint gate verify the diagnosis against telemetry instead of trusting the model's self-reported confidence. The diagnosis already cites the numbers; re-checking them server-side turns an assertion into a fact and makes the gate independent of calibration.” Then #4 (the agent should read ClickHouse, not one replica's memory).

The router

Why a bandit and not a forecasting model?

The router's decisions determine what data it collects. Route away from a gateway and you stop learning about it, including the fact that it recovered. A supervised model trained on routed traffic is trained on a sample its own predecessor selected, and it will confidently recommend the gateway it already prefers. Exploration is what keeps the dataset informative.

Why Thompson over UCB1?

Two reasons. Statistically, probability matching gives smoother allocation than an argmax — it degrades gracefully instead of flipping hard between arms, which matters when gateways have capacity commitments. Operationally, Thompson is stochastic and UCB1 is not, and a deterministic logging policy makes off-policy evaluation impossible. Both showed up in the measurements.

Explain Beta-Bernoulli conjugacy and why it matters at scale.

Beta is conjugate to Bernoulli, so observing a success turns Beta(α,β) into Beta(α+1,β). The Bayesian update is integer addition — O(1) per observation, two floats per arm. At 350M transactions a day that is not elegance, it is the reason it is deployable at all.

What is γ and how did you pick it?

A geometric discount on accumulated counts, giving effective memory of about 1/(1−γ) observations. I did not pick one value — I swept it, and found the optimum moves with transaction volume, because γ forgets per observation while gateways degrade per unit time. 0.999 at 20k/week, 0.9999 at 100k/week, and getting it wrong costs 50–170 bps.

Discount factor or sliding window?

Equivalent in effect; discount is O(1) memory per arm and a window is O(W). At this volume that decides it. Reference is Garivier & Moulines 2011.

Why decay all arms, not just the played one?

Unplayed arms drift back toward the prior, which re-opens them for exploration after a long absence. Decaying only the played arm lets a gateway written off during an outage stay written off forever — which is exactly the PG-Echo failure the environment was built to punish.

Explain the PID controller.

Inner loop is Thompson sampling. Outer loop watches a calibration residual — EWMA of what the router predicted for the arm it chose, minus EWMA of what it got — and when that spikes it divides both Beta parameters by an inflation factor, preserving the mean while widening the variance. It is bounded, self-cancelling doubt. It idles at 1.0 when calibrated, so it costs nothing until the model is genuinely wrong.

Why not use a target success rate as the setpoint?

Two failures. A constant target needs hand-tuning per merchant and cannot distinguish “our model is stale” from “this merchant's traffic is harder”. And max(posterior means) — which I tried first — is a biased estimator of the true max, so the integrator wound up against a permanent positive error and the controller sat at inflation 4.15 instead of 1.0. That bug is why the design is a residual.

Did the controller work?

No, not against a correctly tuned γ, and I report that. Against an untuned posterior it is worth +74 to +80 bps and it recovers about 60% of the tuning gap with no tuning at all. The honest summary is: if you can tune γ per merchant and keep it tuned as volume changes, do that. If you cannot, the controller is the better default.

Why does pid-thompson have the worst outage response?

It deliberately keeps probing the dead gateway at just above the 5% measurement threshold, so the metric records it as never having pulled away. That is a real tradeoff between exploration and outage exposure, and I left it visible rather than moving the threshold.

What does the contextual router's pooling cap do?

It caps prior strength at the pooled evidence that actually exists. Without it an untried gateway gets a full-strength prior at 0.5 — Beta(20,20) at k=40, confidently mediocre — and can never out-sample an arm with real evidence, so the router locks onto whatever it tried first. With the cap an unplayed gateway's prior is Beta(1,1), uniform, which explores. The principle: never be more certain about a cell than the data behind its shrinkage target supports.

The agent

Why hand-write the loop instead of using a framework?

Chapter 17's balanced answer. Name what you own — budgets, termination, error recovery, duplicate suppression, output repair — say those are what page someone, and say the dependency floor is what makes the eval CI-able. Then say you would reach for LangGraph on a team where several people modify the orchestration.

How do you stop the loop from running forever?

Four independent ceilings — steps, tool calls, output tokens, wall-clock — because they fail differently; wall-clock is the one the others do not cover, since a slow provider blows your SLO inside two cheap steps. And every exit path sets a named stop_reason, so there is no branch that can spin. Six named reasons, and the trace store has a column for it.

What happens when the budget runs out?

It spends one final turn demanding an answer rather than bailing. The forcing message forbids further tool calls and instructs the model to set confidence to reflect how little it checked — so budget exhaustion degrades to a low-confidence diagnosis, and because the constraint gate is a confidence threshold, a rushed answer is automatically less likely to move traffic.

How do you handle a tool error?

It is data, not an exception. The dispatcher catches KeyError, ValueError and TypeError and returns a structured error the model can read — with the valid options enumerated, so recovery is possible on the next turn. Only repeated errors break the loop: three consecutive distinct failures trip a circuit breaker.

What if the model repeats the same call?

It gets a nudge instead of the same bytes, keyed on name plus canonically-sorted arguments. And there is a real interaction I documented rather than fixed: dedup fires before the error counter, so a repeated failing call resets the consecutive-error count and the circuit breaker never trips. The loop still terminates via the step budget. Both paths are bounded, but only one is the one you would guess, so there is a test named after it.

Why do all tool results go back in one message?

Splitting them teaches the model to stop issuing parallel calls — it learns from the shape of the transcript, and fragmented results discourage parallelism, which costs latency on every subsequent investigation. There is a test asserting exactly one tool-result message containing both blocks.

How do you stop the model returning unparseable output?

Three layers. Structured outputs constrain decoding to the schema. A dataclass validator re-checks anyway, because a refusal or a truncated stream can still be off-contract. And if it fails, one repair attempt goes back carrying the actual parse error so the model knows what to fix.

Why does the agent have only six tools?

Every extra tool is a chance to pick the wrong one. Each of the six maps to a question an on-call engineer actually asks, and they are all read-only over the same store. The one that earns its place is segment_failures — it is the only way to see a degradation that a fleet-level success rate averages into invisibility.

Why do tools return null instead of a number sometimes?

Below 30 transactions a success rate is noise dressed as signal. Returning null with a note saying the router may have shifted traffic away forces the agent to reason about survivorship rather than reading a number off a dashboard. It is correct behaviour, and one of the three traps named in the v2 prompt is “a null success rate is not a healthy success rate”.

How do you version prompts?

Immutable named versions in source, append-only — never edit V1 or V2, add V3 and move the default. v1-baseline is deliberately naive and kept as the control arm, because without it there is no way to show that later prompt work bought anything. A prompt change is then a reviewable diff and a regression is attributable to the edit that caused it.

Why must system prompts be static strings?

Prompt caching. Tools render before system, so a cache breakpoint on system covers both, and any churn invalidates the prefix. A datetime.now() in there drops the hit rate to zero and nothing fails loudly enough to notice — the only defences are a convention and a trace query plotting cache reads over time.

How is memory implemented, and does it help?

Two tiers: episodic per incident, semantic derived by consolidating repeated patterns — “PG-Bravo has degraded three times, always overnight”, which no single episode contains. Retrieval is IDF-weighted lexical, deliberately, so “does memory help” is not confounded with “is this embedding model good”. It is injected into the brief rather than exposed as a tool, so it is a clean on/off variable. And whether it helps is currently unmeasured — that arm needs an API key and the README says so.

Aren't recalled memories a prompt-injection risk?

They are the closest thing to one here, and they are labelled explicitly as untrusted hypotheses to confirm or reject with tools, not established facts. A memory is a claim written by a previous run of a fallible agent, and treating it as fact is how one early wrong diagnosis becomes permanent. Beyond that, the tools are read-only, and the constraint gate validates every gateway name against the actual fleet before anything moves.

Evals

How do you evaluate an agent?

With real ground truth wherever you can get it. The simulator plants each incident, so the correct scope, gateway, issuer and window are known exactly and grading is ==. A model judge is reserved for the one thing with no ground truth — whether the write-up would help the person who got paged — and reported in separate columns so a fluent wrong answer cannot inflate the headline.

Why is exact match the headline and not partial credit?

A diagnosis that names the wrong gateway is wrong, and the top-line number should say so. Partial credit is reported alongside so progress shows while exact match is still zero, but it is not the number I would put in a release note.

What is Brier score and why do you track it?

(confidence − correct)². Right at 0.9 confidence scores 0.01; wrong at 0.9 scores 0.81. Confidently wrong is the expensive failure in an on-call context — it is what drains a healthy gateway during an incident — and Brier is the metric that names it.

What is segmentation_rate for?

It is a process metric rather than an outcome metric. An agent that never segments cannot be solving the hard cases even when it guesses them right, and outcome metrics cannot see that difference. A right answer reached without the work is one distribution shift from being wrong.

How do you keep the eval from going stale?

Telemetry is cached, so the danger is stale telemetry graded against new ground truth. Two defences: a CACHE_VERSION in the filename that must be bumped when anything shaping telemetry changes, and a CI cache key that hashes every file determining it.

What makes an eval a gate rather than a dashboard?

Exiting non-zero. run_evals.py --gate compares exact match against a committed baseline and fails the build on regression, so a prompt edit that quietly breaks the hard cases does not ship. The subtlety is that a gate can fail open — the baseline file is deliberately un-gitignored, because without it the gate silently passes.

The loop and the negative result

How does a diagnosis become a routing change?

Through from_diagnosis, which refuses more often than it acts. It returns None for low confidence, for fleet_wide and no_incident — neither names a culprit — for an issuer-scoped finding with no issuer, and for any gateway not in the fleet, which is the last barrier against a hallucinated name. Most of the constraint tests test what the layer must refuse to do.

Why does a constraint leak canary traffic?

Because a fully blocked gateway stops producing observations, its posterior freezes, and nothing can ever justify lifting the constraint. That is the same survivorship trap the router already fights, self-inflicted. Canary outcomes feed the posterior like any other, so recovery gets noticed on its own.

Why a TTL?

A constraint written during an incident is evidence about the past, and gateways recover. An immortal constraint is a permanent capacity cut based on a six-hour-old observation. If the fault is still live, the next investigation re-applies it.

What if every gateway ends up blocked?

None are applied. A transaction that reaches no gateway is a guaranteed failure, which is strictly worse than one routed to a suspect gateway. The same fallback exists inside every router's select.

Your closed loop gained +76 bps overall but HDFC was unchanged. Explain.

That is the point of the result. The flat bandit had already rescued HDFC by abandoning PG-Delta wholesale — it just took the fleet's best gateway away from everyone else to do it. The whole gain is in the other-issuers row, +110 bps. The headline is not “we fixed the broken issuer”, it is “we stopped punishing the healthy ones to do it”.

A contextual bandit beat your agent. Doesn't that invalidate the agent?

It invalidates the agent for that failure mode, and I report it rather than tuning the scenario until it wins. For a failure you can enumerate as a dimension, a contextual bandit is simply the better tool. The agent's value is elsewhere: failures nobody enumerated — a fleet-wide event or a diurnal trough mistaken for an incident, which a bandit has no cell for; an explanation a human can act on, which a posterior cannot produce; and no dimensionality cost when the context is card network × issuer × amount band × merchant. The strongest system is both.

Why exactly does the agent trail?

Detection lag plus posterior contamination. The constraint lands 60 minutes in, so the flat bandit has already spent that hour souring on PG-Delta for everyone — and a constraint filters the action, it does nothing to the belief. The posterior underneath is already poisoned by the pre-detection failures and the canary keeps adding a trickle. A contextual bandit never contaminates it, because HDFC's failures only ever touched HDFC's cell.

Off-policy evaluation

How would you decide whether to ship a new routing policy?

Off-policy evaluation on logs the current policy already produced, before anything touches a customer. Ship SNIPS or DR, always report ESS alongside, and treat a candidate far from the logging policy as unevaluable rather than evaluated-badly. Then a small live canary, then a ramp.

Why did IPS return 1.9476?

Rewards are 0/1, so that is not merely wrong, it is incoherent — and nothing in the estimator prevents it. A handful of transactions with tiny logging propensities dominate the average. IPS is unbiased and useless at the same time, which is a good illustration that unbiasedness is not the property you actually want.

What is ESS and why report it?

Effective sample size, (Σw)²/Σw². It is the number that decides whether an estimate means anything: with 11,790 every estimator landed within 15 bps, with 119 IPS was off by 100 percentage points — from the same 40,000 rows. An estimate without an ESS is a number without an error bar.

Why is the Direct Method's confidence interval untrustworthy?

Its variance reflects only the spread of contexts, not how wrong the reward model is. So it reports a standard error of 0.0001 and misses the true value on every candidate — it looks precise and is merely confident.

Can you evaluate a learning policy offline?

No. Importance sampling asks “what if this same decision had been made differently”; it cannot answer “what if a learning policy had seen different data and therefore been in a different state at every subsequent step”. You would need counterfactual histories, which logs do not contain. Freeze the candidate, evaluate the frozen thing, deploy it, then let it learn.

Systems

Design this for 350M transactions a day.

Start with the split: routing is a per-transaction hot path with a microsecond budget and must hold no network calls, so the posterior lives in process and constraints come from a locally refreshed cache. Investigation is a per-incident cold path that calls a model and takes seconds, so it is a separate service with its own SLO. Then state: constraints are low-volume with a natural TTL, so Redis SETEX; posteriors are read per transaction, so a round trip per decision is the budget — snapshot them instead, write-back not write-through. Then the event path: Kafka for durable fan-out carrying propensities, ClickHouse as the columnar store the estimators query. Then degradation: every backend optional, everything fails to in-memory.

Why is Python fast enough?

It probably is not at that volume, and I don't claim it is. What I measured is that the algorithm costs about 11 µs at p50 — 2,400× inside a 100 ms budget — which makes a Go or Rust port a transport decision rather than an algorithmic one. The caveats are printed with the results: it is the decision only, and CPython on one core.

What happens if Redis goes down?

Both stores fall back to in-process state and the service behaves exactly as it did before — it keeps its constraints locally and stops sharing them. A shared-state outage should cost you persistence, not availability. /health reports which backends actually connected, so an unhealthy container is distinguishable from one merely running without Redis.

How do you keep observability from taking down the service?

Every write is wrapped, failures are counted, the warning prints once, and there is a short connect timeout so an unreachable database degrades to “no traces” in seconds rather than blocking on libpq's default. The rule is: observability failing is an annoyance; observability taking down incident response is an outage.

Where would this break first in production?

Take it straight from chapter 19. The multi-replica clock, the Redis TTL unit, and the agent reading one replica's in-memory history instead of ClickHouse. All three are invisible on a single instance and all three are wrong the moment you scale out.

The ones designed to knock you over

General technique

Three moves, in order. Concede the true part immediately — arguing about a fair criticism costs you more than the criticism did. Name the boundary precisely — what the work does and does not establish. Say what it would take to settle it — a concrete experiment, not a hand-wave. Never defend on the ground you have already lost.

It's all simulated. Why should I believe any of it?

“You shouldn't believe it about a real payment network, and the README says so in a section called ‘What is measured, and what is not’. Gateway behaviour comes from hand-specified curves. What the simulation does establish is the thing you cannot establish on production data: with known ground truth I can prove the estimators recover the right answer, the eval grades against a planted incident rather than a judgement call, and the closed-loop comparison has both arms on the same seed. On real data I would have neither ground truth nor a counterfactual arm. The next step is shadow mode against real logs, where OPE is exactly the tool that makes it safe.”

You didn't use LangChain. Isn't that reinventing the wheel?

Chapter 17's balanced answer, then the specific: “the branches I hand-wrote are the ones under test in test_agent_loop.py — every termination path, every recovery path. Behind a framework those are someone else's branches. And the numpy-only floor is what lets the whole eval suite run in CI with no secrets. I did take LangSmith and Langfuse, because those solve problems I didn't want to solve.”

This is a lot of machinery for a problem a contextual bandit solves.

“For the failure mode I tested, yes — and that is my own measured result, in the README. The bandit is the right tool for axes you can enumerate. The machinery earns its place on the two eval cases no bandit over issuers can express — a fleet-wide event and a diurnal trough mistaken for an incident — and on producing a sentence a human can act on. If I were shipping one thing tomorrow it would be the contextual bandit.”

Your live numbers are missing.

“Correct, and it is stated plainly rather than implied otherwise. Everything requiring an API key — the prompt-vs-prompt arm, memory on/off, close_loop --live — is built, tested and wired up, but the numbers reported all come from the deterministic baseline. I'd also want variance across seeds before quoting a live number, because one run of a sampled model is an anecdote, and the gate tolerance cannot be set honestly until that variance is measured.”

Isn't letting an LLM change production routing reckless?

“It would be without the gate, which is why that function is the most conservative code in the repo and refuses more often than it acts — low confidence, no culprit named, no issuer on an issuer-scoped finding, any gateway not in the fleet. Then three properties bound the damage: it never blocks completely, it always expires, and it never blocks everything at once. What is genuinely missing is a kill switch and evidence verification — right now the confidence threshold trusts a number the model writes about itself, and I'd replace it with a server-side re-check of the cited figures.”

Isn't a 75% eval score bad?

“That is the no-model baseline, and it is deliberately not 100%. The eval's first version had six cases and this same heuristic scored 100% — a saturated eval that could not have detected a prompt regression, a memory bug or a model downgrade. Keeping headroom is the point, and there is a test that fails if the baseline ever returns to 100%.”

You wrote your own Prometheus client, your own charts, your own JSON emitter. Isn't that NIH?

“It is a real tension and I applied one rule: a dependency has to earn its place against a specific claim. The claim is that the core library runs on numpy alone, which is what makes the eval suite CI-able with no secrets and no lockfile drift. The Prometheus text format is a documented, stable, sixty-line contract, so that trade is clearly worth it. I would not make the same call for something with real complexity — I took the Anthropic SDK, and I took Redis and Kafka clients in the service layer where the dependency floor doesn't apply.”

What is the weakest part of this project?

Answer honestly and specifically — a candidate who names a real weakness sounds more credible than one who deflects. “Two things. The service layer is single-instance in ways that are invisible until you scale out — the tick is process-relative, the Redis constraint TTL is in the wrong unit, and the agent reads one replica's in-memory history instead of the ClickHouse store that already has the data. And the whole LLM half is measured only against the deterministic baseline, so the prompt and memory arms are wired up and unproven.”

Anything you'd throw away?

“The Haskell DSL is the most defensible thing to cut. It is genuinely good at what it does — an issuer-scoped constraint without an issuer will not compile, a canary rate outside [0,1) is not representable — but it duplicates the fleet definition, its property suite has not been run, and the same invariants exist as tested Python. I'd keep it as a CI gate on hand-authored constraint files and not extend it further.”

Closing move

If they ask what you'd build next

“In order: verify the diagnosis against telemetry before installing a constraint, so the gate stops trusting a self-reported confidence. Move the agent's telemetry read to ClickHouse so it sees all the traffic instead of one replica's. Fix the clock and the TTL unit so constraints actually work across replicas. Then run the live arms and measure model variance across seeds so the gate tolerance can be set honestly. And the interesting research one — have the constraint quarantine the contaminated posterior evidence, not just filter the action, because that is the mechanism the contextual bandit beat me on.”
